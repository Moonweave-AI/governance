# 知識資産の意味論コア

- 重要な知識点はそれぞれ権威ある事実源を一つだけ持つ。他の場所は参照、要約、索引のみ。
- ドキュメントの新規作成または実質的変更の前に、生成されたドキュメントグラフで範囲が重なる有効な記録を確認する。並行する第二の事実源を作らず、既存の権威を再利用するか、明示的に相互リンクした後継を作成する。
- 各ガバナンス文書は少なくとも一つのローカルガバナンス文書へリンクし、ローカル文書グラフ全体を連結に保つ。`related` は双方向、`supersedes` と `superseded_by` は相互のライフサイクル対とする。生成索引はビューであり、第二の事実源ではない。
- Agent はホットアトラスまたは近傍を一つ読む。完全な台帳は監査ビューである。翻訳と置換済み記録は既定の文脈に入れない。
- ホットアトラスには固定の canonical 予算がある。同じ領域に同じタイプがあるとき、新しいホットな canonical 記録は既存記録を置換するか、`consolidation: new-authority` を設定する。
- 変更ログはリリースチェーンである。一つのバージョン、一つの日付、注目すべき変更の短い一覧。そこから変更アトラスを再生成する。追記だけの進捗日記は変更履歴ではない。
- 構築、修正、システム変更は、動作する変更とその証拠で終える。RFC、ADR、計画、索引は、その記録が依頼された成果物である場合、または変更が不可逆な場合の中間ゲートである。防御的な免責の積み重ねは成果物ではない。
- 各意思決定の RFC と ADR は、同じ安定した小文字 kebab-case の `decision_scope` を使う。同じ種類の複数の現行記録は一つの範囲を所有できず、同じ範囲の RFC がある場合は ADR からリンクする。
- 正式なドキュメントは Docs as Code を採用：Git、PR、Review、自動チェック、追跡可能な履歴。
- 正式なドキュメントにはタイプ、Owner、状態、対象読者、更新時刻、可視性、ライフサイクルが必須。
- Tutorial は学習用、How-to はタスク完了用、Reference は事実参照用、Explanation は背景理解用。混在させない。
- RFC は「そうすべきか、なぜか」に答え、ADR は「何が決定され、その帰結」に答え、Design Doc は「どう実装するか」に答え、PR は実際の変更を記録する。
- 研究記録には問題、仮説、コード/データ/モデル/設定/ハードウェア/乱数シード、手法、指標、生結果、ネガティブ結果、限界、再現方法、結論が必須。
